# 用药方案确认时间服务周期强约束设计

## 背景

阶段 3 根据患者明细生成跟踪提醒和用药清单。用户请求中的服务周期为
`2026-09-01 至 2026-09-30` 时，曾出现 userid
`00BBB0DD237E4920B364DDC5544E6B7C` 的用药方案确认时间为
`2026-10-01 08:23:50`，超出服务周期。

现有底层时间生成函数在收到正确服务周期时会限制确认时间，但阶段 3 在提取和构建命令中
重复传入服务周期，且交付前没有独立的确定性校验程序。流程中的参数漂移或未执行正确构建
路径可能绕过已有约束。

## 目标

- 阶段 3 必须接收 `服务周期：YYYY-MM-DD 至 YYYY-MM-DD`。
- 服务周期缺失、格式无效或开始日晚于结束日时停止生成。
- 服务周期在阶段 3 中只解析一次，后续构建与校验复用同一份规范化数据。
- 用药方案确认时间必须位于服务开始日（含）至服务结束日（不含）的范围内。
- 交付前对最终用药清单执行独立校验，越界时报告 userid 和实际时间并停止交付。

## 非目标

- 不修改患者激活时间。
- 不通过截断、回拨或替换方式静默修正越界确认时间。
- 不改变确认时间必须严格晚于激活时间、不得超过激活后 7 × 24 小时、每日位于
  `07:00:00–21:59:59` 的现有规则。
- 不改变跟踪提醒或用药清单的表头、字段顺序和模板样式。

## 请求契约

阶段 3 的触发格式为：

```text
生成跟踪提醒和用药清单 依据文件：<source.xlsx> 服务周期：YYYY-MM-DD 至 YYYY-MM-DD
```

中文冒号和英文冒号均可接受。服务周期是必填参数，日期必须是真实存在的公历日期，且开始日
不得晚于结束日。技能路由、说明文档和代理默认提示必须保持一致。

## 数据流

1. 提取脚本接收并校验服务周期，将规范化的 `serviceStartDate` 和 `serviceEndDate` 写入每条
   患者中间记录。
2. 构建脚本读取提取结果中的服务周期，不再要求代理在构建步骤重新录入日期。
3. 构建脚本确认全部患者记录的服务周期一致，并与源工作簿中的 userid 集合和顺序匹配。
4. 时间生成器使用中间记录中的服务周期生成确认时间。
5. 构建脚本在写出工作簿前再次断言确认时间满足全部时间约束。
6. 独立校验脚本重新打开最终用药清单，按同一份患者中间记录核验每个 userid 的确认时间。
7. 只有独立校验通过后才能向用户交付两个工作簿。

## 时间边界

用药方案确认时间必须同时满足：

```text
确认时间 >= 服务开始日 00:00:00
确认时间 <  服务结束日 00:00:00
确认时间 >  激活时间
确认时间 <= 激活时间 + 7 × 24 小时
07:00:00 <= 确认时间的时刻 <= 21:59:59
```

因此，服务周期 `2026-09-01 至 2026-09-30` 的确认时间最晚为
`2026-09-29 21:59:59`；`2026-09-30` 当天和 `2026-10-01` 均不合法。

如果约束交集内不存在合法时间，生成必须失败并报告对应 userid，不得遗漏患者或生成部分结果。

## 错误处理

- 缺少服务周期：报告阶段 3 缺少必填入参 `服务周期`。
- 日期格式或日期值无效：报告期望格式 `YYYY-MM-DD 至 YYYY-MM-DD`。
- 开始日晚于结束日：报告服务周期顺序错误。
- 中间记录中的服务周期不一致：停止构建并报告数据不一致。
- 最终确认时间越界：报告 userid、确认时间和服务周期，并停止交付。
- 同一 userid 的多条用药记录确认时间不一致：停止交付并报告 userid。

## 测试策略

- 请求契约测试：缺失、无效和逆序服务周期必须失败。
- 时间生成单元测试：使用 userid `00BBB0DD237E4920B364DDC5544E6B7C` 覆盖
  `2026-09-01 至 2026-09-30`，断言结果严格早于 `2026-09-30 00:00:00`。
- 构建集成测试：构建步骤从患者中间记录读取服务周期，不重复接收服务周期参数。
- 失败回归测试：最终工作簿包含 `2026-10-01 08:23:50` 时，独立校验必须失败并报告 userid。
- 边界测试：`2026-09-29 21:59:59` 可接受，`2026-09-30 00:00:00` 及之后不可接受。
- 全量回归：运行阶段 3 相关测试和技能完整性校验。
