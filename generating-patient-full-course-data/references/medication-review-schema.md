# 联合用药合理性与丰富性评估

本文件适用于默认的真实患者模式。明确授权的“虚构测试”模式使用 `fictional-test-mode.md` 的情境记录结构；不得把情境假设填入本文件的原表事实证据，也不得将虚构审核材料用于真实模式导出。

## 目标与证据

丰富性包括不同治疗用途的合理覆盖和等效药物的适当差异，不等同于每人药品数增加。先逐人评估，再汇总同病种；不能以第一个患者的处方作为整批默认方案，也不能为了改变药品名称而更换原表指定产品。请求中的“最少种数：N”只能作为证据阈值：先完成下述主动检索及逐人筛选，若仍不足以支持 N 种，必须停止并报告候选评估结果及缺失依据，不能随机补充病情或药物。

1. 从原表疾病提取明确分型、部位和病程/手术阶段。不能把“创伤后”解释为刚做过手术，不能补充未确诊的合并疾病。
2. 独立评估产品、病因/一线治疗、维持治疗、围手术期治疗、症状支持五类用途。疾病或规范手术本身足以支持某项治疗时，无需人为增加症状字段；需要症状证据的治疗则必须有实际表现。
3. 检索适用于该诊断/部位/阶段的现行指南及最终候选的药品说明书。在 rationale 中记录可查证的指南名称与版本、章节或 URL、药品说明书依据及其如何支持当前用途。不得用“常规用药”“丰富组合”替代具体适应证，不编造引用。无法查证时标明内部排除理由，不猜测给药参数。
4. 年龄用于适用年龄、耐受及剂量评估；性别用于有依据的疾病差异。不得仅因年长添加钙剂、维生素或抑酸药，不得由女性推定妊娠、绝经或哺乳。读取实际 clinicalContext 中的合并疾病、当前用药和安全信息；空字段不等于正常或无禁忌。
5. 对相同治疗用途比较临床等效候选，先检查适应证、治疗线、部位、途径、年龄、过敏、肝肾功能要求、相互作用和重复治疗。通过全部筛选才设 eligible=true；关键风险未排除则为 false。不能只附“启用前核实”就把不确定安全性的药标成可选。
6. 同组可选候选使用既有稳定选择器择一，再完整重建该药的规格、剂量、频次、疗程和监测。跨用途联合需要分别成立，不能将同组候选同时当作联合用药。

## 单药或种数不足时的主动检索

触发条件：源表仅列一种药物、初步筛选后仅一种药物，或初步种数少于用户指定的“最少种数：N”。必须先检索再决定保留单药或停止；不能把“源表只列一种产品”或“症状列为空”当成不检索的理由。

1. 以明确疾病、分型、部位、治疗阶段和现有药物为检索条件，查找一线治疗、联合/辅助治疗以及既有治疗所需的保护措施。优先查阅适用地区的现行专业指南和官方说明书；国际指南需核对人群、部位与本地获批适应证。阅读原文相关章节，不能仅靠搜索摘要、营销页面或 AI 记忆认定可以联用。药品品牌或批准文号不作为向用户索要的必填项；由检索核实通用名、剂型及支持的规格。
2. 区分“可同时联用”“同用途替代”“治疗失败后升级”“短期备用”及“仅特定条件下适用”。不同药物都能治疗同一种病不代表应同时使用；备用药不能为满足种数直接加入每位患者的常规处方。检索还须核对现有产品的证据；指南不支持或存在指南差异时在评估中记录，不能称其为一致推荐的一线治疗。
3. 同疾病/部位/阶段可复用一次查证的文献结果，但须逐人结合年龄、性别、过敏史、当前用药及实际临床背景评估。指南明确由诊断、规范手术或已合理选定治疗支持的用途，可在不虚构症状的情况下成立。需疼痛严重程度、治疗失败、妊娠状态或肝肾功能等关键条件的候选，在条件不明时保留于内部评估并设 `eligible=false`、`selected=false`，说明确切原因；不得把未知写成正常或无禁忌。
4. 在现有 `rationale` 中记录查询词、检索日期、实际查阅的指南名称/版本、URL/章节、说明书及联用条件；在 `candidates` 中记录具体药品、用途、安全筛选和选择/排除理由。不新增 JSON 键，不把文献内容写入原表 `evidence`。无可评估候选时可用空数组，但须写清检索范围和原因。检索失败应说明研究尚未完成，不得伪造来源或声称已经证明不存在联合方案。
5. 只有适应证、联用关系及患者安全条件均成立的药物才能进入最终方案，并生成一一对应的完整处方草稿。有条件候选和替代品不计入已选种数，不得写成患者已在服用。检索与评估后仍低于明确指定的 N，报告实际可支持种数、已评估候选及未满足条件；未指定 N 时可保留有依据的单药或双药。

骨关节炎检索示例：核对外用抗炎药适用部位、何时升级为口服药及其胃保护条件；不得为凑第三种固定加入对乙酰氨基酚，不得把外用无效、消化道风险或其他病情随机补成患者事实。本示例不预设任何三联组合，最终选择依当次适用指南和说明书判断。

## 骨关节炎的评估差异

| 情境 | 需要判断 | 不能直接推定 |
|---|---|---|
| 膝或手部 | 实际疼痛、局部表现、功能影响及局部治疗适用性 | 有诊断就一定需要多药镇痛 |
| 髋或肩等部位 | 深度和药物可达性、该部位指南和说明书支持 | 直接沿用膝/手的外用方案 |
| 继发性或创伤后 | 明确病因、实际治疗阶段及是否存在需单独处理的问题 | 感染、近期手术或抗凝适应证 |
| 已有症状且治疗效果不足 | 核查治疗史、实际疗程、耐受和安全资料，评估替换还是联合 | 自动把药物叠加成固定三联方案 |
| 只有诊断和产品 | 先主动检索并评估五类用途；完成候选筛选后只有原产品适用时允许保留单药 | 随机分配疼痛、炎症或肝肾功能 |

具体药物及剂量由当次可核查依据决定，本表不构成固定药物组合。非药物管理可作为健康管理建议，但不能算入药品数量。

## medication-review.json 契约

JSON 数组必须与患者原表顺序完全一致，每名患者一个 `{userid, roles}`。roles 必须恰好包含 `产品`、`病因/一线治疗`、`维持治疗`、`围手术期治疗`、`症状支持`，顺序不限但不得缺失或重复。

每个 role：

- `role`：以上五类之一。
- `evidence`：非空的 `{field, value}` 数组。field 使用实际原表列名，value 为该患者对应单元格值；比较时仅去除首尾空白并转成字符串。数值 0 和否定表现照实保留，空值不能充当证据。不适用用途也可引用真实疾病或产品类型说明原因。
- `rationale`：非空字符串，写明诊断分型/部位/阶段、临床来源和判断；不得仅引用 userid、年龄或患者标签作为适应证。需症状支撑时在 evidence 引用对应真实症状列。源表、提取 JSON 和引用资料要由生成过程核对。
- `candidates`：候选数组；没有可评估的药物时为 `[]`。
- `exclusionReason`：没有选中药物时必填；说明该用途不适用或风险/关键证据不足。仅内部评估可描述缺失信息，患者工作簿仍禁止占位文案。

每个 candidate：

- `medication`：准确通用名，无首尾空白；同一药在整名患者评估中只列一次，多个用途可在说明中合并。
- `indication`：当前患者对应的具体用途。
- `safetyAssessment`：实际适用性与安全筛选结果，包括已识别的风险及排除情况。不能写成保证安全。
- `eligible`、`selected`：必须是真正布尔值。eligible 表示评估后应保留的治疗候选，不是“理论上可能有用”。不可选不得选中；可选且不属于等效组的药必须选中，否则重新明确其排除依据。
- `exclusionReason`：未选中时必填；同组可选但未选中填写等效择一。已选中时为空。
- `equivalenceGroup`：可选字符串；仅对同用途内的临床等效选项使用同一名称。不分组时省略或为空。组名需要稳定、具体，不能写任意序号来规避重复治疗检查。

等效选择使用 `selectEquivalentCandidate({userid, disease, therapyRole: role + ":" + equivalenceGroup, candidates})`，其中 candidates 只包含本组 eligible=true 的对象并使用 `name=medication`。至少一个候选可选的组必须且只能选一个；零个可选时均排除。

最终 combinedMedication 必须与所有 selected=true 候选完全一致（顺序仍服从产品优先和处方映射规则）。公司产品排除情境应在评估中将该产品排除，再核对过滤后的最终清单。按现有药品过敏及规格规则失败的药物不能通过评估记录绕过。

## 导出及校验边界

调用 `build_workbook.mjs` 必须传 `--review <temp>/medication-review.json`。旧版没有该参数的 CLI 调用需更新；六键 records 与最终十七列模板不变。旧版 evidence 对象格式需重新按实际数据评估为本契约，不能直接批量标 eligible=true。

导出器检查患者覆盖、五类用途、原表值匹配、必填信息、候选状态、等效选择和最终药物一致性；这些是结构与逻辑一致性检查，不能验证文字所声称的临床依据是否可靠，也不能自动识别所有同成分药或相互作用。生成过程仍必须查证临床来源、判读否定表现、复核逐药适应证、安全性与重复治疗。

同病种全相同不自动报错：仅一个可选候选时可以相同。每个多候选组应能追溯筛选和稳定选择结果；不能通过改变疾病、组名、治疗用途、剂量或药品数量强造差异。完成合理评估后 3～5 种可以保留，1～2 种同样有效；不得凑药。

## 与最终交付的关系

本评估 JSON 和检索资料是内部中间文件。“生成患者明细”的最终交付始终为原十七列模板，不得改成评估清单、候选方案或另加评估工作表。只有用户明确另行要求评估文件时才单独输出；这仍不代表患者明细任务完成。

已指定“最少种数：N”时，导出必须传入 `--min-medications N`，按公司产品排除后、已经通过评估的最终药物计数。未选中的候选、等效替代品、待核条件和搜索结果条数均不计入。条件不满足时，在对话中说明未生成请求的患者明细及具体原因；保留内部逐人依据，不用其他文件替代交付，也不复制旧文件充当本次新生成结果。
